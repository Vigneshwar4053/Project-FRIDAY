# Activity & Privacy — Phase 2D-LIVE

All collection and startup/background scopes default OFF. Existing consent decisions persist locally; no private collection was enabled during implementation. Application, browser, title, URL, stored metric, process, connection-count, managed-runtime, login and independent-background scopes have explicit controls. Strict local-only processing cannot be disabled. Screenshots, keys, form contents, password managers, cookies, clipboard, tokens, browser profile history and packet contents are not collected.

## Collection boundaries

The managed GNOME watcher uses only the owner-enabled Focused Window D-Bus extension and Mutter's idle-time interface. It never installs an extension, bypasses GNOME security, reads password fields or changes the desktop session. Managed filters replace sensitive/excluded and unapproved applications with a neutral `__zorvyq_excluded__` marker and blank title before upstream persistence. Approved application identifiers retain blank titles. The neutral marker records a transition boundary without revealing an excluded app or title, and never becomes a ZORVYQ usage row. This permits app metadata with minimal upstream exposure. The extension itself exposes richer window information to local D-Bus clients; review its permission implications before activation.

Firefox monitoring is separately authorized. Only explicitly approved domains and explicit non-private events are accepted. Sensitive authentication pages are excluded, not labeled as successful logins. Reliable login-interaction detection is unavailable: no form inspection, input tracking, credential extraction, or authentication-success inference is attempted. Titles/paths may still reveal private information despite conservative patterns, so their controls default OFF. Browser window titles are never copied through general Firefox application tracking.

URL minimization removes query strings/fragments and rejects embedded credentials, private/local IP sites, unsupported schemes/ports, token-like paths and sensitive patterns. This is conservative metadata filtering, not proof that arbitrary permitted page paths are harmless. Unknown private-state events fail closed. Website categories include conservative defaults plus explicit local custom domain rules; categories describe sites and do not infer the purpose of a particular visit.

## Local processing and lifecycle

ZORVYQ's ActivityWatch transport is fixed to numeric `127.0.0.1:5600`, with finite timeouts, response/event limits, no proxies, redirects, DNS endpoints, server-side query language or API-key discovery. Optional model summaries use selected existing local Ollama models on numeric `127.0.0.1:11434`, reject redirects/proxies, and receive only numeric category totals. Factual answers come from exact permission-approved deterministic queries, never model guesses. No database/filesystem capability or raw titles, URLs, domains, paths or task content reaches the model.

LocalRuntime launches only the reviewed server and GNOME watcher, in private XDG directories with blank window titles, cleared proxy environment, umask 0077 and discarded child output. No tray app, input watcher, sync daemon, telemetry integration or cloud model adapter is launched. This review does not establish zero network activity for every ActivityWatch dependency or independently launched upstream tool. Upstream web UI, extension distribution/update checks, downloads and ordinary browser visits can make external connections. No global internet/firewall changes were made.

Disable/Stop monitoring prevents further ZORVYQ ingestion; Pause prevents all new writes and hides current activity. In-process controls serialize against the consumer, discard in-flight reads after scope changes and terminate owned children. An independent background consumer observes changed preferences on its next three-second cycle plus bounded in-flight request time; database write guards recheck consent. `systemctl --user stop zorvyq-awareness.service` immediately requests graceful termination of that entire service. A GUI control does not terminate independently started upstream watchers or uninstall browser extensions. Stop those separately and manage/delete their richer upstream history separately.

Saved application approval does not imply Start Monitoring at Login. That toggle defaults OFF. Independent background operation requires a separate dialog naming the exact user-service file, logout behavior and login operation. Only that user unit is written; existing GUI autostart is preserved. The service's IPAddressAllow/Deny directives are additional best-effort user-systemd isolation, not a verified firewall audit.

## Storage and controls

The existing `~/.config/zorvyq/activity.sqlite3` (or XDG-config equivalent) remains separate from My Tasks, assistant memory and cybersecurity knowledge. Its permissions are 0600, new directories 0700, and exports 0600/new files only. Owner/symlink checks, integrity checks, bounded queries, transactional migrations, atomic source reconciliation, indexed UTC timestamps, and deletion replay suppression protect the local history. SQLite secure-delete is enabled per connection. The database is not encrypted; filesystem snapshots/backups and OS-account compromise are outside these controls.

Schema v5 adds website categories, monitoring sessions, named timeline views and a singleton minimized live status. It preserves existing activities. Current status expires after 20 seconds and is invalidated by privacy scope changes. Completed and interrupted intervals remain distinct; current heartbeats never enter Last 3 Activities as completed. Browser records remain separate details and do not double-count application totals. No records are seeded.

Activity retention defaults to 30 days, metrics to seven; both accept 1–3650 days. Hourly cleanup runs during authorized collection. Clear/delete/export and current application/domain exclusions are available in Activity & Privacy / Activity History. Turning off title/URL controls clears those fields in ZORVYQ's existing history; process/network revocation removes their persisted metric fields. Upstream data is unaffected. Existing historical app/domain records can be deleted explicitly; narrowing an allowlist does not silently erase past history.

History can be incomplete during outages, unapproved applications, stale/missing/ambiguous sources or saturated API responses. The consumer retrieves a bounded overlap and expands actual idle evidence for long overlapping foreground intervals; no pre-consent/downtime activity is invented. Long outages that fall outside the overlap can leave gaps. ActivityWatch idle classification is an estimate. Metrics are sampled once per minute; displayed values carry a sample timestamp and are not instant hardware measurements.

## Verification boundary

Synthetic backend/offscreen GUI tests cover privacy, current/complete state, duration, outages, consent, permissions and history. Python-level offline checks deny DNS and external socket connections with synthetic event sources; they do not certify the full desktop while physically disconnected. A separate real server-only smoke check confirmed HTTP 200 and loopback-only binding, then stopped the disposable server. No real desktop watcher, Firefox recording, live model inference, reboot test or owner application-switch acceptance was performed. See the LIVE report for exact test results and the owner procedure.
